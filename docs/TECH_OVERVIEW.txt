============================================================
  ABDS - Arsenal Base Deck Simulator  技術概要
============================================================

■ アクセスURL
  https://sekimiya.github.io/abds/

■ ホスティング構成
  ┌─────────────────────────────────────────────────────┐
  │  フロントエンド: GitHub Pages (gh-pages ブランチ)    │
  │  バックエンド DB: Supabase (PostgreSQL)              │
  │  カードデータ: 静的JSON (GitHub Pages から配信)      │
  │  カード画像: 公式サイトから直接参照 (hotlink)        │
  └─────────────────────────────────────────────────────┘

  - GitHub Pages で静的ファイル(HTML/JS/CSS/JSON)をホスト
  - フロントエンドから Supabase REST API を直接呼び出し
    (デッキ保存・いいね・コメント・短縮リンク等)
  - カードデータは事前ビルドした静的JSONファイルで配信
    (card_index.json / card_details.json / link_index.json / tactics_cards.json)
  - PWA対応で Service Worker によるオフラインキャッシュ
  - アプリ内には画像データを一切持たず、公式サイトの画像キャッシュを転用する形で画像表示を実現
  - アプリ内では、公式画像キャッシュデータ+解析済みカードデータDBを突合してUIに表示

============================================================

■ 画像ゼロホスティング × OCRデータ突合（コア設計思想）

  このアプリは「カード画像を1枚も自前でホストしない」。
  約3000枚×表裏の画像データを持たずに、リッチなカードUIを実現している。

  仕組み:
  ┌────────────────────────────────────────────────────────────┐
  │                                                            │
  │  [公式サイト]                    [ABDS独自データ]          │
  │   gundam-ab.com                   (OCRで生成)              │
  │   ├─ カード表面画像 (.jpg)        ├─ 能力値 (攻/防/HP)     │
  │   └─ カード裏面画像 (_b.jpg)      ├─ スキル・リンク効果    │
  │         │                         ├─ 地形適性              │
  │         │                         ├─ 特殊能力 (EB/SQ/AB)   │
  │         ↓                         └─ テキスト全文          │
  │  ユーザーのブラウザが                    │                  │
  │  公式URLに直接アクセス                   │                  │
  │         │                               │                  │
  │         ↓                               ↓                  │
  │  Service Worker が               静的JSON (GitHub Pages)   │
  │  Cache API に自動保存             data/card_details.json    │
  │  (card-images-v1)                       │                  │
  │         │                               │                  │
  │         └──────────┐  ┌────────────────┘                  │
  │                    ↓  ↓                                    │
  │              フロントエンドで突合                           │
  │         「この画像 = このカードデータ」                     │
  │                    ↓                                       │
  │            リッチなデッキビルダーUI                         │
  │                                                            │
  └────────────────────────────────────────────────────────────┘

  ポイント:

  1. 画像は公式サイトにアクセスしてキャッシュとして保持（画像を保持せずあくまでキャッシュ）（hotlink）
     - <img src="https://www.gundam-ab.com/images/cardlist/card/AB01-001.jpg">
     - アプリサーバーに画像を一切保存しない

  2. Service Worker による透過キャッシュ
     - 初回アクセス時に公式URLをfetch → Cache APIに自動保存
     - 2回目以降はキャッシュから即座に返却（オフラインでも表示可能）
     - ユーザーが「キャッシュ作成」ボタンで全カード一括DLも可能
       (8並列の<img>プリロードでSW fetchイベントを発火)
     - opaque response (no-cors) で公式CORSポリシーを回避

  3. 公式サイトにないデータをOCRで独自生成
     - 公式サイトは「カード画像」しか提供していない
     - カード裏面の能力値・スキル・効果テキストは
       画像の中にしか存在しない（構造化データなし）
     - Claude Vision でカード裏面画像をOCR →
       攻撃力/HP/スキル効果等を構造化JSONとして抽出
     - つまり「公式が提供していないデータベース」を
       AI OCRで自動構築している

  4. カード番号をキーにした突合
     - 画像URL: IMG_BASE + cardNumber + ".jpg"
     - OCRデータ: card_details.json[cardNumber]
     - 同一のカード番号で画像とデータを紐付け
     - 画像がキャッシュ済みなら公式URL、未キャッシュなら
       プレースホルダーSVGを表示（公式に不要な負荷をかけない）

  結果:
     画像ストレージ0 + ホスティング無料(GitHub Pages) で
     5000枚のカードを表裏画像付き・全能力値付きで
     検索・比較・デッキ構築できるアプリを実現

============================================================

■ プロジェクト概要

  ガンダムアーケードカードゲーム「アーセナルベース」の
  デッキシミュレーター。
  公式サイトからカードデータをスクレイピング →
  AIでOCR → デッキビルダーUIまでフルスタックで構築。

============================================================

■ アーキテクチャ全体像

  公式サイト (gundam-ab.com)
    ↓ BeautifulSoup スクレイピング (fetch_cards.py)
  カードメタデータ + 画像URL
    ↓ 画像DL (download_card_images.py)
  ローカル画像 (OCR用)
    ↓ Claude Code CLI (Vision) — card_ocr_cc.py
    ↓ Stage1: 生テキスト抽出
    ↓ Stage2: 構造化JSON生成
  カードDB (~3000枚)
    ↓ 静的JSON生成 (generate_derivatives.py)
  data/*.json (GitHub Pages で配信)
    ↓ Vanilla JS フロントエンド
  PWA (Service Worker + IndexedDB + localStorage)

============================================================

■ 静的フロントエンド × 動的サイトの連携と切り分け

  本アプリは「サーバーを持たない静的サイト」でありながら、
  デッキ投稿・いいね・コメント・共有リンクといった
  動的機能をフルに備えている。
  これを実現するのが「静的HTML + Supabase BaaS」の構成。

  【ページ構成と役割分担】

  ┌─────────────────────────────────────────────────────────┐
  │ 静的ページ（読み取り専用のカードデータ）                │
  │                                                         │
  │  index.html      デッキエディター (デスクトップ)        │
  │  mobile.html     デッキエディター (モバイル)            │
  │                                                         │
  │  → data/*.json を fetch して表示                        │
  │  → カード検索・フィルタ・デッキ構築はすべてクライアント │
  │  → サーバーへの問い合わせ不要（完全静的）               │
  ├─────────────────────────────────────────────────────────┤
  │ 動的ページ（Supabase経由のユーザー投稿データ）         │
  │                                                         │
  │  decks.html          デッキ一覧・投稿サイト (PC)        │
  │  decks_mobile.html   デッキ一覧・投稿サイト (モバイル)  │
  │                                                         │
  │  → Supabase REST API を直接呼び出し                     │
  │  → デッキ閲覧・いいね・コメント・削除                   │
  └─────────────────────────────────────────────────────────┘

  【ページ間の連携フロー】

  index.html (デッキエディター)
    │
    │ ① デッキ構築完了 → 「投稿」ボタン
    │    Supabase /rest/v1/decks に POST
    │    (デッキ名・作者・カード10枚・タクティクス・パスワードハッシュ)
    │
    │ ② デッキ共有 → 短縮URL生成
    │    Supabase /rest/v1/short_links に INSERT
    │    デッキコードをハッシュ化して重複排除
    │    → 短縮URL: index.html?s=XXXXX
    │
    │ ③ 共有URLからデッキ復元
    │    ?s=XXXXX → Supabase から deck_code を取得
    │    ?d=XXXXX → URLパラメータから直接デコード
    │    → デッキエディターにカードを自動配置
    │
    ├────────→ decks.html (デッキ一覧サイト) へ遷移
    │
    decks.html
      │ ④ デッキ一覧表示
      │    Supabase /rest/v1/decks_public (VIEW) を GET
      │    + /rest/v1/comments を並列取得
      │    → クライアント側でデッキとコメントを突合
      │
      │ ⑤ いいね
      │    Supabase RPC: increment_likes (サーバー側関数)
      │    → localStorage でいいね済みを管理（二重防止）
      │
      │ ⑥ コメント投稿
      │    Supabase /rest/v1/comments に POST
      │
      │ ⑦ デッキ削除
      │    Supabase RPC: delete_deck_with_password
      │    → パスワードハッシュ(SHA-256)で認証
      │
      │ ⑧ デッキをシミュレーターで開く
      │    index.html?d=<deck_code> にリダイレクト
      │    → エディターでデッキを再現
      │
      └────────→ index.html に戻る

  【なぜ自前サーバーなしで動的機能が実現できるか】

  ┌────────────────────────────────────────────────────────────┐
  │                                                            │
  │  通常のWebアプリ:                                         │
  │    ブラウザ → 自前APIサーバー → DB                        │
  │    (認証・バリデーション・ビジネスロジックをサーバーで実行)│
  │                                                            │
  │  ABDSの構成:                                               │
  │    ブラウザ → Supabase REST API → PostgreSQL               │
  │    (サーバーレイヤーをBaaSに完全委譲)                      │
  │                                                            │
  │  Supabase が提供するもの:                                  │
  │  ├─ PostgREST: テーブルを自動でREST APIとして公開         │
  │  ├─ RLS (Row Level Security): 行レベルのアクセス制御      │
  │  ├─ RPC: PostgreSQL関数をHTTPエンドポイントとして公開     │
  │  │   └─ increment_likes: いいね数のアトミック加算          │
  │  │   └─ delete_deck_with_password: パスワード検証+削除     │
  │  ├─ Views: decks_public ビューで公開データのみ返却        │
  │  └─ anon key: フロントエンドから直接呼べる公開APIキー     │
  │                                                            │
  │  → 自前サーバー0台で CRUD + 認証 + RPC を実現             │
  │                                                            │
  └────────────────────────────────────────────────────────────┘

  【データの流れまとめ: 静的データ vs 動的データ】

  ┌──────────────┬────────────────────┬──────────────────────┐
  │ データ種別   │ 配信元             │ 更新頻度             │
  ├──────────────┼────────────────────┼──────────────────────┤
  │ カード情報   │ 静的JSON(GitHub)   │ 新弾追加時のみ       │
  │ カード画像   │ 公式サイト(直参照) │ 公式更新に自動追従   │
  │ デッキ投稿   │ Supabase(動的)     │ ユーザー操作でリアル │
  │ いいね       │ Supabase RPC       │ ユーザー操作でリアル │
  │ コメント     │ Supabase(動的)     │ ユーザー操作でリアル │
  │ 短縮URL      │ Supabase(動的)     │ 共有時に自動生成     │
  │ テキスト修正 │ Supabase(動的)     │ ユーザー報告         │
  │ デッキ(WIP)  │ localStorage(端末) │ 編集の都度オートセーブ│
  └──────────────┴────────────────────┴──────────────────────┘

  【切り分けの設計判断】

  - カードデータは「事前ビルド済み静的JSON」
    → 新弾追加時だけ OCR → JSON生成 → git push すれば反映
    → 99%の時間はDBアクセス不要。CDN配信で高速・無料

  - ユーザー投稿データは「Supabase BaaS」
    → CRUD + いいね + コメント + 削除（パスワード認証付き）
    → PostgreSQL関数 (RPC) で不正操作を防止
    → decks_public ビューで公開列のみ返却（内部データ非公開）

  - 編集中デッキは「localStorage」
    → オフラインでも編集可能
    → サーバーに保存するのは「投稿」操作時だけ
    → 端末ごとに独立（プライバシー保護）

  - モバイル/デスクトップの振り分け
    → UA判定で自動リダイレクト
    → index.html ↔ mobile.html
    → decks.html ↔ decks_mobile.html
    → 同一Supabaseを共有（データは共通）

■ バックエンド / データパイプライン (Python)

  - Flask + Gunicorn/gevent (管理・OCR用サーバー)
  - 3,300行超の app.py に40以上のAPIルート
  - ETag + stale-while-revalidate によるHTTPキャッシュ最適化
  - 起動時にカードインデックスを事前シリアライズ(バイト列化)
  - Supabase (PostgreSQL) でデッキ永続化
    フォールバックとしてJSONファイル
  - SQLite (WALモード) でリクエストメトリクス記録
  - Flask-Compress (gzip) / Flask-Limiter (200req/min)
  - Basic Auth / Bearer Token / Cookie / Query Param の4層認証

■ OCR パイプライン（最大の技術的特徴）

  Claude Code CLI の Vision 機能を使った
  カード裏面の2段階OCR:

  ┌──────────┬──────────────────┬────────────────────────┐
  │ ステージ │ 入出力           │ 目的                   │
  ├──────────┼──────────────────┼────────────────────────┤
  │ Stage 1  │ 画像→_raw.json   │ 忠実なテキスト抽出     │
  │ Stage 2  │ Raw→_basic.json  │ ゲームデータとして構造化│
  └──────────┴──────────────────┴────────────────────────┘

  なぜ2段階?
    → ゲームのルール変更やデータ構造変更時に
      Stage 2だけ再実行すれば済む。
      画像の再OCR（コスト大）が不要。
      生テキストを保持することで、llmによる高costな画像認識タスクを削減して、
      トークン消費の軽い簡単なテキスト要約のみでDBの再構築を行える

  - サブプロセス実行 + 300秒タイムアウト + 最大3回リトライ
  - バックグラウンドスレッドで非同期処理
  - 管理画面からOCR進捗をリアルタイム監視可能

============================================================

■ フロントエンド（フレームワークなし）

  - Vanilla JS のみで5,300行超のデッキビルダーUI
    (React/Vue等のフレームワーク依存ゼロ)
  - デスクトップ版 + モバイル版
    (UA検知で自動振り分け)
  - PWA対応: Service Worker で3層キャッシュ
    - App Shell Cache (HTML/CSS/JS)
    - Data Cache (JSON API)
    - Image Cache (カード画像)
  - IndexedDB でカード詳細をクライアント側キャッシュ
  - localStorage でデッキデータ永続化 + オートセーブ
  - html2canvas でデッキのスクリーンショット出力
  - リアルタイムでコスト計算・リンク発動判定・SQ/EB表示
  - CSSアニメーション（コスト超過時のグロウ演出等）
  - ダークテーマ (#0f0f0f ベース)
  - CSS変数によるカラーシステム
    殲滅: Red / 制圧: Blue / 防衛: Green
    SQ: Pink / EB: Orange / AB: Purple

■ 技術的に面白いポイント

  1. LLM Vision × OCR
